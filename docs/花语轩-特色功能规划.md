## A. 商品与选购体验（9 项）

### A1. 多规格 SKU 与差价
- **价值**：同款花束按「11 枝 / 19 枝 / 33 枝」「包装配色」「是否带花瓶」拆分，客单价可提升 20%+，避免为每个规格建一条商品。
- **实现要点**：新增 `product_spec`（规格名/值）与 `product_sku`（组合、加价、独立库存与编码）；购物车行 `cart_item` 加 `sku_id`，扣库存改为扣 SKU；`ProductView` 输出 `skuList`，详情页加规格选择条；`OrderItem` 落 `skuText` 与 `skuCode` 快照。
- **依赖**：`Product.stock` 需拆分到 SKU 级（迁移脚本把现有库存写成默认 SKU）。
- **优先级 / 成本**：P0 / L

### A2. 搭配购与组合套餐
- **价值**：「花束 + 香薰 + 贺卡」打包价，提升连带率；婚庆/开业场景可配大套餐。
- **实现要点**：`bundle` 主表 + `bundle_item`；下单时套餐按一条 `OrderItem` 记录并展开子项快照；详情页与购物车「加 ¥X 换购」条；库存按子项最小值计算可售套数。
- **优先级 / 成本**：P1 / M

### A3. 详情页「搭配推荐 / 相似花礼」
- **价值**：把单一入口流量转成浏览深度，鲜花品类高度依赖灵感型购买。
- **实现要点**：一期用规则召回（同分类 + 标签交集 + 价格带 ±30%），离线预计算写 `product_relation` 表并 `@Cacheable`；二期接共购矩阵（`order_item` 自连接算 lift），无外部依赖。
- **依赖**：已有 `tags` 与分类树。
- **优先级 / 成本**：P1 / M

### A4. 花语 / 养护知识库并挂到详情页
- **价值**：鲜花最强差异化内容是「花语 + 能活多久 + 怎么养」，直接降低犹豫与售后。
- **实现要点**：`care_guide`（花材、天数、光照、换水频率）+ `flower_meaning`（花材×颜色→寓意文案）；详情页新增「养护卡」抽屉；贺卡文案可一键引用花语（与已交付的贺卡功能天然联动）。
- **优先级 / 成本**：P1 / M

### A5. 商品对比栏（最多 3 件）
- **价值**：枝数/花材/尺寸相近的商品决策成本高，对比可显著减少跳出。
- **实现要点**：localStorage 存对比集 + 底部浮动条；`/compare?ids=` 服务端渲染参数表；对比字段走 `ProductView` 白名单避免敏感字段泄漏。
- **优先级 / 成本**：P2 / S

### A6. 库存紧张与到货订阅
- **价值**：鲜花供给波动大，「仅剩 3 束」促单 + 缺货留资挽回流失。
- **实现要点**：详情页库存 ≤ 阈值显示紧迫感条；`stock_alert`（用户、商品、状态）；后台补货入库时触发批量通知任务；订阅按钮复用现有收藏交互。
- **依赖**：需要 A27 消息通道才有闭环。
- **优先级 / 成本**：P1 / M

### A7. 限时闪购场次
- **价值**：造节奏、清边角库存，是鲜花这种短保品最自然的促销方式。
- **实现要点**：`flash_session`（起止、状态）+ `flash_item`（商品、闪购价、限购、场次库存）；下单链路按场次价覆写单价并单独扣减场次库存（条件 UPDATE，与已实现的乐观扣减同一模式）；首页倒计时楼层。
- **优先级 / 成本**：P1 / L

### A8. 商品短视频 / 360° 展示　✅ 3D 部分已交付（真实花束 glTF 模型）
- **价值**：鲜花是视觉品，动态展示比 5 张静图更能建立质感信任。
- **实现要点**：`Product.mediaType/mediaUrl`，`<video>` 懒加载与首帧封面；素材仍走本地 `static/upload`，不引入外链（保持当前零外网请求）。
- **优先级 / 成本**：P2 / S

### A9. 商品分享海报与专属二维码
- **价值**：社交裂变成本最低的入口，用户常把花束图发到群里问「好不好看」。
- **实现要点**：纯 JDK `Graphics2D` 合成长图（商品主图 + 名称 + 价格 + 带 `?from=uid` 的二维码），避免引第三方绘图库；海报下载计入 `search_keyword` 式的渠道埋点。
- **依赖**：二维码生成器（可用 zxing 单 jar，注意需重启进程才能加载新依赖）。
- **优先级 / 成本**：P1 / M

## B. 下单与履约（10 项）

### B1. 时段运力日历（预约定时达的下一步）　✅ 已交付
- **价值**：已交付的「预约定时达」只校验时段合法性，还没管**约满**；母亲节当天超载会直接砸口碑。
- **实现要点**：`delivery_slot_quota`（日期 + 时段 + 上限 + 已占用），选时段时按日拉日历并置灰已满；`/api/shipping/quote` 增加 `slots` 字段，前端把 `datetime-local` 换成「日期 + 时段」两级选择。
- **依赖**：`ShippingPolicy`（已存在）。
- **优先级 / 成本**：P0 / M

### B2. 电子贺卡高级排版（手写体 / 边框 / 照片）
- **价值**：贺卡是情感载体，样式越丰富溢价越高，可做成付费增值项。
- **实现要点**：`card_message` 支持受限标记（换行 + 白名单标签，复用 `HtmlSanitizer`）；上传小图作背景（走本地存储 + 尺寸裁剪）；付费样式挂 `card_style.price` 并进订单明细。
- **依赖**：已交付的贺卡与打印样式。
- **优先级 / 成本**：P1 / M

### B3. 收花人通讯录与纪念日簿
- **价值**：把「一次性买家」变成「年年复购的人」，是鲜花最核心的留存资产。
- **实现要点**：`recipient`（姓名/电话/地址关系/备注）+ `anniversary`（收花人、日期、类型、提醒提前量、绑定商品）；列表页「一键下单」直接跳到结算页并预填；生日字段 `user.birthday` 可作为默认条目来源。
- **优先级 / 成本**：P0 / L

### B4. 周期送花订阅（每周一花）
- **价值**：预收现金流 + 锁定长期需求，订阅制是鲜花行业验证过的最优模型。
- **实现要点**：`subscription`（期数、周期、支付方式、状态）+ 定时任务按周生成子订单（复用 `OrderService.create` 保证同一套计价与库存规则）；暂停/跳过/改期入口；订阅看板统计续订率。
- **依赖**：B5 自助改期、A27 消息通道。
- **优先级 / 成本**：P1 / L

### B5. 用户自助改期 / 改址 / 改时段
- **价值**：送花场景极易临时变动，自助改能砍掉大半客服电话。
- **实现要点**：仅 `pending`/`paid` 且未发货可改；改期重走 `ShippingPolicy.requireSlot` 与运费重算，差额走补付/退款流水；变更写 `order_trace`（`code='changed'`）保留原值。
- **依赖**：已交付的状态机与轨迹。
- **优先级 / 成本**：P1 / M

### B6. 地图定位与配送范围判定
- **价值**：同城闪送按半径收费比按「方式」收费更合理，也能明确告诉用户「您不在配送范围」。
- **实现要点**：地址保存时离线计算坐标（内置城市中心坐标表 + 区级偏移，不引外部地图 API 以保持零外网）；`same_city` 按距离分档计费，`ShippingPolicy` 扩展 `feeByDistance`；地址表单加「定位」按钮。
- **优先级 / 成本**：P2 / L

### B7. 无接触配送 / 放置偏好 / 是否电话联系　✅ 已交付　✅ 已交付
- **价值**：后疫情时代已成为默认期待，一句话备注远不够结构化。
- **实现要点**：`Order` 加 `delivery_preference`（枚举：当面签收 / 放门口 / 放前台 / 放快递柜）、`contact_preference`；后台打印面单与配送卡片展示为醒目徽标。
- **优先级 / 成本**：P1 / S

### B8. 门店 / 花艺师派单与接单
- **价值**：多门店后必须知道「这单谁做、谁送」，也是履约时效考核的基础数据。
- **实现要点**：`store` + `craftsman`（可服务时段、接单上限）；`Order.storeId/craftsmanId`；派单规则先按配送区域 + 负载最少，后台可手工改派；改派写 `order_trace`。
- **优先级 / 成本**：P2 / L

### B9. 缺货自动拆单与部分发货
- **价值**：鲜花常单品断货，整单卡住会同时损失体验与周转。
- **实现要点**：`order_parent_id` + 子单独立状态/运费；发货台勾选缺货行 → 生成补发子单并沿用原券差额逻辑（券只分摊一次，避免重复抵扣）。
- **依赖**：优惠券分摊口径要先落到行级。
- **优先级 / 成本**：P2 / L

### B10. 电子发票与报销凭证
- **价值**：企业送礼、婚礼采购的硬需求，缺失直接丢大单。
- **实现要点**：`invoice_request`（抬头、税号、邮箱、关联订单、状态）+ 后台开票工作流；PDF 用模板渲染，抬头信息校验必填规则；金额按实付（含运费、不含退款）。
- **优先级 / 成本**：P1 / M

## C. 营销与增长（10 项）

### C1. 阶梯满减与下单返券
- **价值**：把已交付的单券能力升级成「凑单杠杆」，客单价提升最直接。
- **实现要点**：`promotion`（满 X 减 Y 多档、可叠加标记）与 `coupon` 并存，`CouponPolicy` 之上加 `PromotionPolicy` 统一裁决；「返券」在支付成功事件里发放 `user_coupon`，与已实现的取消退券对称。
- **优先级 / 成本**：P0 / M

### C2. 会员成长值与等级权益
- **价值**：`user.memberLevel` 目前只有 ordinary/vip 两档且手动设置，缺成长路径就缺复购动机。
- **实现要点**：`growth_value`（消费额、单数、评价数加权）+ `member_tier`（折扣、包邮门槛、生日券、专属客服）；等级变化写审计与站内信；`ShippingPolicy.freeOver` 支持按等级覆盖（银卡 199、金卡 99）。
- **优先级 / 成本**：P1 / L

### C3. 积分商城与积分过期
- **价值**：积分只有抵扣一条出口会被当成折扣工具，兑换能沉淀活跃。
- **实现要点**：`points_goods`（实物兑换扣积分与库存）+ `points_log`（收支流水，已发放/收回/过期分列，配合已实现的下单/退单积分正负账）；FIFO 过期批次表。
- **优先级 / 成本**：P1 / L

### C4. 邀请有礼与反作弊
- **价值**：鲜花是强推荐品类（婚礼、开业、探病都是口碑场景）。
- **实现要点**：`invitation`（邀请人、被邀请人、状态、奖励发放时间）+ 注册页 `?inv=` 参数；奖励双向发放但设「首单完成后才发」，配 IP/设备/手机号频次限制与风控名单。
- **依赖**：A27 通知 + 风控计数。
- **优先级 / 成本**：P1 / M

### C5. 拼团 / 砍价
- **价值**：社群团长（写字楼、社区群）能带来低成本批量订单。
- **实现要点**：`group_activity`（成团人数、时限、团价）+ `group_record`（成员、状态）；到期未成团自动全额退款（复用 `closeOrder` 的回补链路）；库存按「占用 → 成团转实扣」两段式。
- **优先级 / 成本**：P2 / L

### C6. 礼品卡 / 储值与转赠
- **价值**：花是最常见的「不知道送什么就送花」的礼物，礼品卡能预收现金并拓新客。
- **实现要点**：`gift_card`（面值、卡号+提取码、状态、绑定用户）+ 支付时选择余额卡；下单支付流水扩展多资金来源；转赠即解绑再生成提取码。
- **依赖**：支付模型要先支持「一单多来源」。
- **优先级 / 成本**：P2 / L

### C7. 节日会场可视化搭建
- **价值**：花店 80% 的量集中在 5 个节日，会场页现在只能改模板。
- **实现要点**：`landing_page` + `page_block`（类型：轮播 / 商品楼层 / 券楼层 / 富文本）+ 生效时间；后台拖拽排序，前台 `/p/{slug}` 渲染；发布前生成预览链接（带 token）。
- **优先级 / 成本**：P1 / L

### C8. 购物车降价提醒与收藏降价播报
- **价值**：把「犹豫」转成「回访下单」，是零成本转化。
- **实现要点**：`cart_item`/`favorite` 记录加入时价格快照；价格变动或每日任务比对后生成消息 + 列表页「比加入时降 ¥x」徽标。
- **优先级 / 成本**：P1 / S

### C9. 企业/团购客户专属价与对公结算
- **价值**：一束花毛利 30 元，企业月框 500 束就是稳定现金流。
- **实现要点**：`company` + `company_member` + 协议价（商品级或折扣率）；结算走对公转账 + 后台核销；发票（B10）联动。
- **优先级 / 成本**：P2 / L

### C10. 精准人群推送（RFM 分群）
- **价值**：券发给对的人才是营销，发所有人是补贴。
- **实现要点**：定时任务按近 90 天 R/F/M 打分并打 `user_segment` 标签；后台定向发券（已有）升级为「按分群批量发」，附 A/B 对照组与转化率回收。
- **依赖**：已交付的后台定向发券。
- **优先级 / 成本**：P1 / M

## D. 用户与账户（7 项）

### D1. 短信验证码登录 / 注册 / 换绑
- **价值**：鲜花消费场景多在移动端，记不住用户名是第一道流失。
- **实现要点**：`sms_code`（手机号、用途、6 位码、有效期、失败次数）+ 频控（同号 60s / 单日 10 次）；本地开发用「控制台打印 + 固定测试码」的 Mock 通道，生产切真通道（A27）。
- **优先级 / 成本**：P1 / M

### D2. 第三方登录（微信 / QQ OAuth）
- **价值**：注册摩擦最低路径，同时拿到头像昵称。
- **实现要点**：`user_auth`（provider、openId、用户）支持一账号多绑定；回调 state 走签名 Cookie 同套密钥；首次登录落到「绑定手机号」步骤避免僵尸账号。
- **优先级 / 成本**：P2 / M

### D3. 登录二次校验（TOTP）与设备管理
- **价值**：后台账号一旦被拖库直接影响资金与用户数据。
- **实现要点**：`user_totp`（密钥、启用、恢复码）+ 登录时二次校验；`login_device` 记录 UA/IP/最近登录，支持远程下线（会话失效需配合 Redis 会话外置化 F6）。
- **优先级 / 成本**：P1 / M

### D4. 账号注销与数据导出
- **价值**：合规要求，也是信任背书。
- **实现要点**：注销走软删 + 冷静期 15 天（期间登录可撤销），订单保留但脱敏 `receiverPhone`；导出为 ZIP（订单 CSV + 地址 JSON），与 `AdminOrderController.export` 复用 CSV 工具。
- **优先级 / 成本**：P1 / M

### D5. 浏览足迹与偏好画像
- **价值**：支撑 A3 推荐、C7 会场个性化，也能做「你可能还喜欢」。
- **实现要点**：`browse_history`（用户、商品、停留秒数、来源）异步写入避免拖慢详情响应；偏好标签按分类/价格带/色调统计，个人主页展示。
- **优先级 / 成本**：P1 / M

### D6. 地址簿增强：智能识别与常用排序
- **价值**：鲜花下单地址填写错误率最高，直接造成履约事故。
- **实现要点**：粘贴整段文本 → 正则切分姓名/手机号/省市区/详址；按「最近使用 + 送达成功率」排序；保存时做重复地址合并提示与行政区校验。
- **优先级 / 成本**：P1 / S

### D7. 家庭/亲情账户与代付
- **价值**：子女给父母订花、异地给伴侣送花是典型结构。
- **实现要点**：`family_group`（主账户、成员、角色）+ 下单选「由主账户支付」；额度与月度上限防止滥用；账单页合并展示。
- **优先级 / 成本**：P2 / M

## E. 内容与互动（7 项）

### E1. 站内消息中心
- **价值**：目前订单/券/公告都靠页面跳转提示，缺一个统一「未读」入口，是所有自动化功能的落地口。
- **实现要点**：`user_message`（类型：交易/营销/系统；标题、正文、跳转、已读）+ 头部铃铛角标 + 列表分页；事件发布用 Spring `ApplicationEventPublisher`，监听器异步落库，失败只告警不影响主流程（与已交付的 `trace()` 容错策略一致）。
- **优先级 / 成本**：P0 / M

### E2. 评价追评、商家回复与图片审核
- **价值**：UGC 是鲜花转化的第一信任源；一条差评不回复伤害翻倍。

### E3. 买家秀 / 晒单社区
- **价值**：花本身就是内容，UGC 池可反哺商品详情与会场素材。
- **实现要点**：`post`（作者、图片、正文、话题、关联商品、审核状态）+ 点赞收藏；话题页与商品页「晒单」楼层；订单完成事件引导发布并发券（C1）。
- **优先级 / 成本**：P2 / L

### E4. 花艺师主页与作品集
- **价值**：把「谁做的」显性化，是差异化定价与粉丝复购的抓手。
- **实现要点**：`craftsman`（简介、擅长风格、作品集、评分）与商品/订单关联；主页列出其制作评价（脱敏）；下单页可「指定花艺师」（配合 B8）。
- **优先级 / 成本**：P2 / M

### E5. 养护提醒推送
- **价值**：送花后第 2/4/7 天提醒换水剪根，是把「一次性交易」变「被记住的服务」的最便宜方式。
- **实现要点**：签收事件生成 N 条延时消息（`scheduled_message` + 定时任务扫描）；文案取自 A4 养护知识库按花材匹配。

### E6. 客服工单与 FAQ
- **价值**：花损、延误、错送需要留痕与赔付口径，现在只有取消原因一个自由文本字段。

- **优先级 / 成本**：P1 / L

### E7. 心愿单与「他人送我花」

## F. 后台运营与治理（9 项）

### F1. RBAC 多角色与权限点
- **价值**：现在只有 `userType=customer/staff` 的二分，店长、花艺师、客服共用超级后台是最大合规风险。
- **实现要点**：`role`/`permission`/`user_role` + 拦截器按 URL 模式与权限码鉴权；数据权限（仅本店订单）在查询层强制加条件；后台菜单按权限渲染；变更写 `admin_audit_log`（已存在）。
- **优先级 / 成本**：P0 / L

### F2. 采购与供应商管理
- **价值**：鲜花成本 60% 在花材采购，没有采购单就没有真实毛利。
- **实现要点**：`supplier` + `purchase_order` + `purchase_item`；入库生成批次（F4），成本移动加权更新 `product.cost`；采购建议由安全库存 × 近 7 日销量驱动。
- **优先级 / 成本**：P1 / L

### F3. 库存盘点与出入库流水
- **价值**：目前库存只被下单/退单改变，任何人工调整都无痕。
- **实现要点**：`stock_move`（类型：采购入库/销售出库/退货/盘盈盘亏/报损，关联单据号）；所有库存变更收敛到 `StockService` 单一出口；盘点单支持差异确认。
- **依赖**：现有 `ProductRepository.increaseStock/decreaseStock` 改为内部方法。
- **优先级 / 成本**：P0 / M

### F4. 花材批次与损耗登记
- **价值**：鲜花是短保品，批次化管理才能算出真实损耗率与「临期先出」。
- **实现要点**：`product_batch`（入库日、保质期、数量、剩余）；出库按先进先出核销；到期前 N 天进报损队列并生成促销建议（联动 A7 闪购）。
- **优先级 / 成本**：P2 / L

### F5. 成本与毛利分析看板
- **价值**：定价与促销决策现在全靠感觉。
- **实现要点**：行级成本快照（下单时冻结 `cost`）→ 看板按商品/分类/活动维度算毛利、券成本、运费成本与净贡献；导出 CSV 复用 `AdminOrderController.export` 模式。
- **依赖**：F2/F3 提供成本来源。
- **优先级 / 成本**：P1 / M

### F6. 履约 SLA 与超时预警
- **价值**：已交付的支付超时自动取消是单点，全链路超时（未接单/未发货/未在承诺时段送达）才是口碑。
- **实现要点**：`order_sla_rule`（状态 × 阈值 × 动作）+ 定时扫描，命中后写 `order_trace`（`code='sla_warn'`）并推送 E1 消息；后台列表加「即将超时」筛选与红点。
- **依赖**：已有 `cancelPayTimeoutOrders` 定时任务模式。
- **优先级 / 成本**：P1 / M

### F7. 危险操作二次确认与权限内审批
- **价值**：退款、改价、删商品现在是单人一键生效，资损无护栏。
- **实现要点**：金额阈值以上触发「双人复核」队列（`approval_request`）；前端统一二次确认组件（`huAdmin.confirmDelete` 已有雏形，扩到全量危险操作）；审批结果通知申请人。
- **优先级 / 成本**：P0 / M

### F8. 定时任务可视化中心
- **价值**：支付超时取消、券到期提醒、分群计算都在代码里，运营看不见也手动不了一次。
- **实现要点**：`job_definition`（bean 方法白名单、cron、启停）+ `job_run`（耗时、结果、异常）；支持「立即执行一次」并强制幂等；所有 job 必须返回处理条数以复用现有日志口径。
- **优先级 / 成本**：P1 / M

### F9. 功能开关与灰度
- **价值**：新特色功能（配送、贺卡这类）能先放 10% 流量或只放某门店，出问题秒级关闭。
- **实现要点**：`feature_flag`（key、表达式、白名单、百分比）+ 拦截渲染；前端按 `/api/config/flags` 隐藏入口，后端在裁决点判分支（绝不能只靠前端隐藏）；变更进审计。
- **优先级 / 成本**：P1 / M

## G. 技术与可靠性（8 项）

### G1. 下单接口幂等　✅ 已交付
- **价值**：网络重试 / 双击会造成重复下单，是最典型的资损口子。
- **实现要点**：进入结算页发一次性 token（`idempotency_token`，条件 UPDATE 消费），`/api/orders/create` 缺 token 直接 409；同 token 重放返回首次结果。不依赖 Redis。
- **优先级 / 成本**：P0 / M

### G2. 接口与用户级限流
- **价值**：秒杀、闪购、登录接口必须有限速，否则一次活动就打穿。
- **实现要点**：Caffeine 本地滑动窗口（已有 Caffeine）+ `@RateLimit` 注解，超限返回 429 语义的统一 `Result`；单机限流即可满足当前规模，多机部署时再换 Redis 令牌桶。
- **优先级 / 成本**：P0 / M

### G3. 全链路 traceId 与结构化日志
- **价值**：现在排查一笔订单要按时间点猜，有 traceId 才能一串到底。
- **实现要点**：Filter 生成 traceId 放 MDC + 响应头；日志 pattern 输出 JSON；定时任务与事件监听器手动继承父 traceId。
- **优先级 / 成本**：P1 / M

### G4. 图片处理：缩略图、WebP 与去重
- **价值**：`static/img/products` 与用户上传图无尺寸治理，首屏与流量成本高。
- **实现要点**：上传时同步生成 3 档缩略图（`Graphics2D` 或引入 Thumbnailator）；`<img srcset>`；按 SHA-256 去重命名；SVG 保持现状（商品占位图已本地化）。
- **优先级 / 成本**：P1 / M

### G5. 对象存储抽象层
- **价值**：目前素材硬绑本地磁盘；换 MinIO/OSS 不应改业务代码。**注意**：历史项目遗留的 OSS AccessKey 已泄漏在 git 记录中，必须先吊销，新密钥只从环境变量注入。
- **实现要点**：`StorageService` 接口（put/get/url/delete）+ 本地实现为默认；配置前缀 `flower.storage.*`，凭据走 env；上传白名单与大小校验放接口层。
- **优先级 / 成本**：P1 / M

### G6. 数据库每日备份与恢复演练
- **价值**：`ddl-auto=update` + 单库，一次误删就没了；交付前必须有可回滚路径。
- **实现要点**：`pg_dump` 定时任务 + 滚动保留 14 天 + 校验和；每周自动恢复到临时库并跑行数一致性检查，结果进 F8 任务中心。
- **优先级 / 成本**：P0 / S

### G7. 敏感字段加密与脱敏分级
- **价值**：手机号、地址、贺卡留言（含情感隐私）现在明文可查。
- **实现要点**：JPA `AttributeConverter` 做 AES-GCM 列加密（密钥来自 `FLOWER_*` 环境变量）；查询字段（如手机号登录）另存哈希列；导出与后台列表按角色分级脱敏（现有昵称脱敏 `测**户` 的做法推广到手机号/地址）。
- **优先级 / 成本**：P1 / L

### G8. CI + 容器化 + 端到端冒烟
- **价值**：32 个单测全靠本地手跑，回归成本会随功能数线性上升。
- **实现要点**：GitHub Actions（`mvnw verify` + 失败阻断）；`Dockerfile` + `docker-compose`（app + postgres + 可选 redis）；Playwright 覆盖「注册 → 搜索 → 加购 → 用券 → 下单 → 支付 → 后台发货 → 签收 → 评价」一条主链路。
- **优先级 / 成本**：P1 / L

## I. 地图与地理智能（高德开放平台）（16 项）

> 依托 `.env` 中的三把高德密钥：`map_web_key`（Web 端 JS API）、`map_web_secure_key`（JS API 安全密钥）、
> `map_web_service_key`（Web 服务端：地理编码 / 行政区域 / 天气）。
> 服务端调用一律走 `AmapClient` 代理，**Web 服务端密钥绝不下发到浏览器**；JS 侧只注入 Web 端 key。
> 与 B6「地图定位与配送范围判定」的分工：B6 只做「能不能送」的布尔判定，本板块做的是「看得见、讲得清、算得出」的地理表达层。

### I1. 鲜花产地溯源地图　✅ 已交付
- **价值**：鲜花是产地强相关品类，「云南斗南直采 / 海拔 2100m 日照」这类事实是最便宜 also 最可信的转化素材；把产地摆到地图上，等于把供应链透明度和品质承诺一起卖给顾客。
- **实现要点**：新表 `flower_origin`（产地名、adcode、经纬度、海拔、主营品种、直采故事、生效花期）+ 商品→产地关联；`/api/map/origins` 下发点位；`/map/origin` 页用高德 JS API 打 marker + 右侧产地卡；商品详情页显示「这束花来自哪里」并可一键跳到地图定位；产地坐标优先取迁移脚本内置值，缺失时用地理编码回填。
- **依赖**：`AmapClient`（地理编码）、高德 JS API 安全密钥配置。
- **优先级 / 成本**：P1 / M

### I2. 货物运输路线可视化　✅ 已交付
- **价值**：等花的过程中，顾客真正焦虑的是「花到哪了」。一张带折线和进度感的路线图，比一串物流单号更能压住催单和差评，也是空运冷链/海运保鲜这类高运费方式的合理性证明。
- **实现要点**：以订单为轴拼出「产地 → 分拨中心 → 配送城市 → 收花地址」四点折线，各点地理编码后落 `order_route`（或随订单派生）；高德 `Polyline` 分段着色（已行驶实线 + 在途呼吸动画 + 未发车虚线），配 `MovingMarker`；里程用球面距离 × 线路系数估算，剩余时长按 `ShippingPolicy.arriveAt` 口径复用，避免与承诺时间两套数；自提单只画「门店 → 你」的末端段。
- **依赖**：I1 产地、`order_trace`、`ShippingPolicy`。
- **优先级 / 成本**：P1 / M

### I3. 销售数量地理分布热力地图　✅ 已交付
- **价值**：管理层第一个问题永远是「哪些城市在长、哪些在掉」。区域表 + 气泡大小比数字表直观一个量级，也直接指导分拨中心与运力投放。
- **实现要点**：`Order` 按收货城市聚合（订单数、销量枝数、实付金额），`/api/map/sales` 输出带经纬度的区域榜；地图用气泡（半径 ∝ 销量、色阶 ∝ 同比）+ 城市标签，前台 `/map/sales` 面向顾客展示「已送达 N 座城市」的社会证明，后台数据看板复用同一接口做经营视角；支持分类与时间窗筛选。
- **依赖**：地址城市字段清洗（省/市拆分已具备）、`AnalyticsService`。
- **优先级 / 成本**：P2 / M

### I4. 配送城市天气与鲜花养护提示　✅ 已交付
- **价值**：高温天送花是运损和差评的高发区。把天气前置到结算页，既能顺势推荐空运冷链（客单价与履约安全双赢），也能让顾客收到「今天 34℃，我们加了冰袋」这类可验证的照顾感。
- **实现要点**：`AmapClient.liveWeather(adcode)` 实况 + 预报，Caffeine 缓存 10 分钟（城市粒度、失败短路返回空而非抛错）；`FlowerCareAdvice` 纯函数规则表：高温→建议冷链/冰袋、降雨→提醒收花人在家、干燥→养护卡加一句换水频率；结算页与订单详情展示天气条，结论同时写进 `order_trace` 的「配送安排」节点，客服与后台可回溯。
- **依赖**：`AmapClient`、`ShippingPolicy`（推荐方式的运费差额）。
- **优先级 / 成本**：P1 / S

### I5. 我的花田养成（天气联动、成熟送人）　✅ 已交付
- **价值**：鲜花是低频消费，养成是把人留下来的钩子——每天回来浇水顺手就看到新品和券包，DAU 与复购一起抬；而「养熟了送给妈妈」把游戏结果转成一次真实下单，比签到送积分更有情感落点。

- **依赖**：I4 天气、`UserCoupon` 发放、积分体系。
- **优先级 / 成本**：P1 / L

### I6. 花车实时位置追踪
- **价值**：同城闪送最有杀伤力的一屏——「花车离你还有 1.2 公里」。等待焦虑直接换成分享欲，也是骑手与客服扯皮的终结者。

### I7. 门店自提地图与就近推荐

- **价值**：送错楼是鲜花差评的头号来源，手填地址天然缺失经纬度。让下单人在地图上点一下，比事后电话确认便宜得多。

### I9. 配送范围可视化圈选与超区拦截

- **实现要点**：后台地图多边形编辑器保存 `delivery_zone`（GeoJSON），下单前用射线法判断收花点是否落在区内，区内/区外分别给运费与时效；超区直接给出「暂不配送 + 就近可送地址」的解释文案，并留一个转人工入口。
- **依赖**：I8 经纬度、后台地图编辑组件。
- **优先级 / 成本**：P1 / M

### I10. 地理围栏到达自动播报
- **价值**：骑手进入收花人 2 公里自动发提醒，比手动点「我已出发」可靠，也把「不在家/电话打不通」的失败签收率压下来。
- **实现要点**：以收花点为圆心建半径围栏，位置上报命中即写 `order_trace` 并触发提醒（短信/站内信，接 E1 消息中心）；离开半径自动撤销一次，避免重复骚扰。
- **依赖**：I6 位置上报、E1 消息中心。
- **优先级 / 成本**：P2 / M

### I11. 一天多单路径优化（活动/婚礼批量送花）
- **价值**：婚庆、开业、企业年会是鲜花的高客单场景，但一次十几单的排线靠人排既慢又容易漏单，接了不敢做等于没接。
- **实现要点**：按分拨点/门店为起点，对当日待送点做最近邻 + 2-opt 排序，高德 `/v3/direction/driving` 取真实里程核算成本；输出建议顺序与时间窗冲突提示，后台可拖拽微调后下发给骑手。
- **依赖**：I8/I9、B8 派单。
- **优先级 / 成本**：P2 / L

### I12. 产地天气与花期上市日历
- **价值**：产地端天气决定到货品质和价格波动。提前知道斗南连续降温，就能在进货与定价上抢一周先手，也能对顾客说清「这一批为什么少」。
- **实现要点**：对 `flower_origin` 逐个拉 `/v3/weather/weatherInfo?extensions=all` 预报，累计成产地风险标记；与 `product.arrival_date` 合成上市日历，风险产地商品的详情页降级为「预售/顺延」提示。
- **依赖**：I1 产地、I4 天气。
- **优先级 / 成本**：P2 / M

### I13. 干线温控曲线与运损理赔
- **价值**：空运冷链和海运保鲜卖的是「花况完好」，出问题时必须有温度证据；没有曲线的理赔全是口舌之争。
- **实现要点**：`cold_chain_log`（订单、时间点、温度、湿度、设备号），路线地图上叠加温度带（正常/预警/超标）；超标自动生成运损工单并关联理赔政策与退款。
- **依赖**：I2 路线、F4 批次损耗。
- **优先级 / 成本**：P2 / L

### I14. 送花足迹地图
- **价值**：把「我在花语轩送出了 37 束、落到 12 座城市」可视化，是零成本的情感资产和朋友圈传播素材，也是老客召回的钩子。

### I15. 后台运营地理看板
- **价值**：老板问的是「华东为什么掉、华南该不该建仓」，答案必须落在地图上，而不是又一张 CSV。

- **价值**：超出自营运力的订单直接丢掉最可惜，转给合作花店既保住 GMV 又拿到佣金，还能把网络覆盖讲成融资故事。
